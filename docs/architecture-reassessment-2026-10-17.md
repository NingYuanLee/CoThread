# CoThread 架构、健壮性与性能复评

日期：2026-10-17。对象：`D:/work/dsh-coThread` 当前未提交工作区，包含此前八阶段优化。不是对已部署版本的鉴定。

## 总体结论

当前架构适合单实例、受控规模继续使用和迭代。领域边界与异步资源所有权已有明确规则，正常关闭、连接故障与聊天乱序读取获得了针对性回归支持。现有证据不足以证明高并发、多实例故障接管和长时间运行的稳定性。

复评后的推进：第九阶段已复现并修复“检测失锁后，旧候选读取仍驱动队列写入”的问题，增加工作器专属可撤销数据库访问视图；297 项无数据库测试及相关真实数据库定向回归通过。它只约束检测失锁后的本进程数据库访问，已经发出的数据库/外部操作及检测前窗口仍未原子隔离，下面第一项风险仍需继续推进。细节见持续优化记录第九阶段。

第十阶段进一步修复超量命令输出先杀父进程、后台子进程仍写文件的问题，并补齐无效 UTF-8 解码后膨胀的输出限制。当前 302 项无数据库测试与本轮 4 项数据库/运行时回归通过。任意父进程已退出、沙箱重连、服务强退后的回收及 Linux 分支仍未完整验证，下面第三项风险已有阶段性修复但尚未关闭。

第十一阶段已修复同进程重连句柄无法回收原命令、旧句柄可重建已删除目录的问题，增加弱实例登记与回收入口管理，并验证异步 mkdir/write、并发回收、创建期间重连和失败重试。当前 309 项无数据库测试与本轮 4 项数据库/运行时回归通过；跨进程、服务强退、任意父进程已退出及 Linux 回收边界仍未关闭。

第十二阶段建立长会话空增量基线：100/1,000/4,000 条历史消息分别返回约 77 KB/757 KB/3.03 MB JSON，即使没有新消息，回复、请求和更新仍随历史增长。等价查询合并候选在 4,000 条历史上由 17.08 ms 退化为 38.90 ms，未采用。新增固定消息游标仍观察旧任务完成、用量更新和删除的契约回归，相关 6 项数据库测试通过；下一步需要侧表自己的变更/删除游标协议。本轮保留生产实现，不能将测量误报为性能提升。

第十三阶段已接入显式 opt-in 的侧表快照指纹：未变时省略重复集合，变化和删除时重发完整快照，保留每次鉴权和旧协议。4,000 条历史的本轮成对样本响应从 2,721,272 降至 1,366 字节，SQL 仍为 16 条；319 项纯测试、7 项聊天数据库回归、类型构建与真实接口浏览器隔离验收通过。它解决未变传输放大，尚未减少数据库扫描，也不等同于持久的行级增量协议。

优先补齐锁丢失后的旧任务隔离、长会话读取规模和运行容量观测。现阶段没有证据支持为了扩容而立即引入微服务或额外消息系统。

## 已建立的工程基础

- React 工作台 → HTTP/MCP → 领域服务 → MySQL；文档内核保留唯一写入边界，Service/任务模块有反向依赖及循环依赖门禁。
- HTTP 与 worker 分用数据库池，入口配置分别为 8 和 16 个连接。命名锁统一管理，获取/释放确认不明的连接销毁；事务回滚失败不再归还状态不明的连接。
- 工作器 stop 等待在途工作；HTTP、SSE、开发预览升级连接参与排空，最后才关闭连接池。重复停止共享完成过程，设置 30 秒总期限。
- 前端缓存及实时连接使用请求身份/代次防止旧成功或错误覆盖新状态，聊天游标由服务端已读取窗口推进。
- 已有请求 ID、Server-Timing、慢请求记录，以及执行器锁状态健康信息；具备进一步建立容量基线的入口。

## 当前最重要的风险

### 1. 高优先级：锁丢失后，旧在途任务尚缺贯穿执行链路的隔离

事实：`server/replies.js:278` 默认每 15 秒核查所有权；`stopAll` 在约 394 行停止新任务并等待已有任务完成。`server/work-events.js` 的 stop 同样是排空，不会取消已经进入的 work。服务入口调用 worker 时未传入 `onLockLost`。

影响判断：MySQL 已释放旧连接的锁之后，新执行器可能取得所有权，而旧任务尚未结束。正常关闭持锁排空不能覆盖这种情形；已有会话锁、条件更新等局部保护也不能直接证明所有外部副作用都被隔离。本轮未复现实际重复写入，不把它描述为已发生事故。

建议验收：阻塞一次已开始的外部任务，故障注入使执行器专用连接失效，启动接管方，再放行旧任务；逐条核对旧任务写入、外部调用与沙箱状态。根据结果增加任务代次校验、提交前所有权检查、可取消操作及副作用幂等保护。

### 2. 高优先级：聊天消息已分页，多个侧表仍按完整历史读取

事实：`server/service-iterations.js:181` 起，reviews、replies、updates、requests、connectorTasks 仍按 thread_id 选择完整集合，没有沿用消息窗口的游标。大 output/diff 已投影，pending 已使用序号范围扫描，但这不改变上述记录集合的增长方式。

影响判断：长会话每次轮询的数据库读取、JSON 序列化和前端状态处理成本仍可能随历史增长。已有单查询优化不能代表整条接口的规模问题已经消失。

建议验收：固定新增消息为 0 或 4，按不同历史长度与并发数采样接口 P50/P95、SQL 行数、响应字节、Node CPU/RSS、池等待。优化必须保留旧消息上仍活跃的任务、状态变化和引用锚点，不能简单只返回当前页关联行。

### 3. 中高优先级：沙箱正常超时已有覆盖，异常终止边界仍不完整

事实：`server/local-sandbox.js:131` 起使用 execFile，maxBuffer 为 6 MiB，回调被忽略；另有自定义输出监听和进程树终止器。terminate 在直接子进程已有 exitCode/signalCode 时直接返回。正常命令期限和显式 kill 走树回收，超量输出或父进程先退出的行为仍需独立验证。

影响判断：直接父进程结束不能作为整个进程树已结束的充分证据。不能从现有正常超时回归推断 maxBuffer、异常父进程退出和服务强制退出同样安全。本轮未制造失控子进程，不声称已复现泄漏。

建议验收：限定在独立临时沙箱内，测试超过输出上限、父进程提前退出、子进程保留管道等场景；检查退出结果、后台标记及进程树，并在 Windows/Linux 分别验证。

### 4. 中优先级：运行健康与执行器可服务状态需要分开消费

事实：`server/http-app.js:67` 的健康接口在主数据库可读时报告 status=ok；锁查询失败记录 lockError，执行器停止通过 localActive/lostReason 表达。接口有信息，但 HTTP 200 不等于任务执行服务可用。

建议：核查部署侧是否针对执行器未运行、锁归属异常、任务积压与失败率设置独立告警；以排队时间、连接等待、事件循环延迟和 RSS 曲线建立容量边界。当前评审未检查部署监控配置，不声称这些告警一定缺失。

### 5. 中低优先级：前端维护复杂度与加载成本仍有优化空间

当前 `Documents.tsx` 2,065 行、`WorkspaceApp.tsx` 1,926 行、`SystemManagement.tsx` 1,571 行；协调器 1,338 行。行数是审阅与状态归属核查的线索，不是性能结论，应沿职责和状态所有权拆分。

生产构建仍提示 office-preview 同时静态和动态导入。产物中存在约 1.47 MB 的 elk chunk 等重型模块；不能把文件总量当作首屏实际下载量。需浏览器网络瀑布和交互采样后，再确定拆包收益。本轮没有作界面或 HMR 可用性验收。

`registerDevServerUpgrade` 会销毁非代理路径的 upgrade，开发入口又与 Vite HMR 共用 HTTP server。这是待实测的监听器协作风险；未经浏览器验证，不认定 HMR 已不可用。
