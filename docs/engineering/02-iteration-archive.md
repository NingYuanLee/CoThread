# 迭代背景、归档与交接

迭代的「背景与目标」与「对话」「轨迹」并列展示。进行中的可写成员可以调整；小祥可依据事实与成员明确表达的方向调用 `update_iteration_context`，必须提供原因。变更前后内容、操作者、来源和原因写入 `iteration_context_changes`。方向不明确时先提醒成员，不限制群聊；Chat 模式保持只读。

页签使用左右布局：左侧展示当前背景和目标；右侧按管理空间单列表排列搜索、功能按钮、表格和底部分页。「变更背景与目标」是功能区里的主按钮，弹窗编辑并填写备注。搜索区的「查询」使用同一主题色主按钮；night 深色主题里该色为蓝色。变更记录按时间倒序展示。搜索匹配发起者、审核者、备注和变更前背景与目标，可筛已审核或未审核。每条包含发起者、审核者、变更前背景和目标、备注及时间。`GET /api/threads/:id/context-changes?page=1&pageSize=10` 另接受 `q` 与 `review`（`all`、`reviewed`、`pending`），仅对有迭代访问权的成员开放，每页最多 50 条。`108_iteration_context_reviewer.sql` 增加可空的 `reviewed_by` 字段；尚无审核记录时显示「未审核」，普通 PATCH 不接受客户端伪造审核者。本次不增加新的审核流程。

## 权限与状态

迭代创建人保存在 `threads.created_by`。只有仍有项目访问权的创建人或当前 `projects.project_leader_id` 能发起、撤回、重试或确认归档；项目管理员身份不单独赋予归档权。

- `active`：正常讨论、任务和背景目标变更。
- `archiving`：普通业务只读，老翁整理独立的归档方案，人类可调整、撤回或最终确认。
- `archived`：保留最终快照与处置结果。

发起归档使用与上下文运行时相同的会话锁，并在事务中取得迭代行锁、检查运行项、固定快照并切换状态。消息与任务变更、任务接受和启动、小祥/子 Agent 及本地执行器启动同样锁定迭代，避免归档检查和执行启动同时通过。存在运行中任务或执行实例、助手回合、工具、沙箱、本地执行器、上下文同步或压缩时，返回具体阻塞项，保持原状态。

未执行的待确认、待指派或阻塞任务可以进入归档方案；进入归档中后，排队工作不再启动。所有原迭代消息、任务、背景目标及提交审核操作均受服务端检查，归档流程专用记录和只读访问除外。项目共享文档库不全局冻结；快照保存引用的精确版本。

## 老翁与人类决策

复用原有老翁 `iteration_archive` 会话与 `agent_laoweng_runs`，以 `archive_phase` 区分草案和长期记忆两个阶段。草案包含实时结论、每个未完成任务的留档/交接建议、其他事项和承接迭代的名称、背景、目标。准备阶段不更新项目长期总结，也不写入原迭代聊天或业务任务。

人类确认须覆盖全部未完成任务，不能混入其他任务。交接必须同时创建承接迭代；没有交接任务时也可选择只把背景与其他事项承接到新迭代。不创建时，事项随原迭代留档。

最终确认在一个事务中完成：

1. 固定人类确认的结论、处置及原任务快照。
2. 留档任务仅标记 `retained_at`，保留真实业务状态。
3. 交接任务保留 ID 和 execution run 历史，`origin_thread_id` 延续现有代码约定作为当前所属迭代，`original_thread_id` 保存最初来源，`agent_task_iteration_moves` 记录每次交接；新迭代重新分配展示编号。小祥责任转给新迭代会话，排队执行记录收口后重新调度。
4. 原迭代变为已归档，原排队回复、请求和执行适配队列收口。
5. 排队给同一老翁更新项目长期总结。
6. 在同一事务写入项目记忆：一条核心议题 / 问题复盘，一条里程碑 / 迭代归档。出处是这次归档和相关任务。重复确认不另写。改记忆不改群聊。长期总结仍只由随后的记忆任务更新。

确认以工作流 ID 幂等执行，重复请求返回同一承接迭代。撤回、重试通过运行令牌区分代次；迟到模型结果不能写回已经撤回或替换的方案，撤回与最终确认只能有一个成功。整理失败保持归档中，允许重试或撤回。

新任务必须属于迭代；历史无迭代任务兼容读取和原有管理。保留任务的迭代不能被删除，避免外键置空使任务脱离迭代。

## HTTP 接口

| 方法  | 路径                               | 作用                                 |
| ----- | ---------------------------------- | ------------------------------------ |
| PATCH | `/api/threads/:id`                 | 更新进行中迭代的背景、目标及变更原因 |
| POST  | `/api/threads/:id/archive`         | 检查并进入归档中，排队整理           |
| GET   | `/api/threads/:id/archive`         | 读取归档方案、整理状态与当前操作权限 |
| POST  | `/api/threads/:id/archive/cancel`  | 撤回当前归档代次                     |
| POST  | `/api/threads/:id/archive/retry`   | 重试失败的方案整理                   |
| POST  | `/api/threads/:id/archive/confirm` | 按人类决定归档及可选创建承接迭代     |

撤回和重试携带 `workflowId`；确认另带 `conclusion`、`taskDecisions`、`notes`、`createNextIteration` 和 `nextIteration`。方案状态为 `preparing`、`ready`、`failed`、`cancelled`、`completed`。历史已归档迭代没有新版方案时返回 `null`，原归档快照继续可读。

迁移：`106_iteration_archive_workflow.sql`、`107_iteration_context_changes.sql`。专项回归见 `tests/iteration-archive.test.js`；旧最终归档场景通过 `tests/archive-helper.js` 完成两阶段流程。
