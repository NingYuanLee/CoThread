# 项目进程与项目现状设计

2026-11-03 追加：记忆两态、三来源治理、固定历史出处与最新验证边界，以 [按来源治理方案及实施记录](20-memory-source-lifecycle-plan.md) 为准。

2026-11-04 简化：项目现状收敛为每项目一份 Markdown（`project_status`），随项目进程结算覆盖；旧的唯一现状节点、修订、来源快照与每日巡检已删除。历史变化由项目进程条目承担。

## 定位

项目进程记录项目发展中有持续影响的变化、阶段成果和决定，解释发生了什么、为什么以及影响；不复制任务日志或将所有系统事件自动变成记忆。每个重要节点单独保存，关联议题、任务、文件和可核验出处。

项目现状不是记忆条目，而是每项目一份纯正文：只写当前阶段、已确认成果或能力、正在推进事项、明确阻碍与待解决问题，不重复项目目标和背景，也不逐条重述历史节点。用自然段落表达，不写标题、列表符号、加粗等 Markdown 修饰。项目进程结算提交新增或更新的条目时整份覆盖，不保留修订；历史变化由项目进程条目承担。

项目目标、背景仍由原有项目资料维护。其有实质影响的变化可形成普通项目进程节点，记录变更前后、原因和影响；文字润色不自动建条。作业不得修改目标或背景。

## 触发与输入

事件按七层过滤：只接项目、迭代、任务的新增或变化；先过滤不主要的行为，再过滤不主要的任务和迭代；主要任务、主要迭代和项目本身的主要行为才进入记忆判断。

- 项目主要行为：创建、简介/目标/背景实质变化、成员构成变化、归档恢复。立即触发。
- 迭代主要行为：目标/背景变更、归档、迭代级关键决定。没有任务、消息很少且无核心议题的迭代归档不触发。
- 任务主要行为：终态、阻塞、返工（重新打开）。开始、进行中等普通状态流转不触发。
- 主要任务判定：正式任务、失败过、重试过、返工过、阻塞过；只有命中的任务才单列，普通任务只合并进任务分布。
- 主要任务若直接命中迭代目标、高度匹配项目简介，或结果改变项目级约束、风险、阶段，同时写项目进程；普通任务完成不升级。
- 其余候选（如文件、关联组、议题进展）只入候选池，按 ≥40 条或 ≥20 分钟批量处理，不单独触发结算。手动刷新始终可用。

事件只触发判断，零产出合法。短时间内同一变化的多个事件可合并。

输入包括事件时间和稳定来源、可用的变更前后值、相关讨论及决定、任务和文件、已有项目进程索引、当前现状 Markdown、当前目标背景。目标背景只作为理解上下文，不写入现状复述。重大变化需要可靠的历史值和原因；记录不足时标注缺口，不从当前值倒推。限制上下文时保留可追溯来源及覆盖范围，必要时按需补读。

只读工具默认在项目权限范围内查询相关记忆和原始出处；模型提出结构化建议，程序验证来源身份与权限并写入。来源存在不等于自动证明内容，应核对事实是否有依据；无法确认时降级为待核实或不写。

## 输出与存储契约

普通节点至少包含标题、事件或适用时间、背景、变化或成果、影响、来源和相关记忆。目标或背景变化应尽可能明确变更前后及原因。项目现状是一份覆盖式正文，仅表达已确认现状；进行中和阻碍须有有效来源，过时或不可确认的信息标记待核实，不能猜测完成或停滞；正文不带标题、列表或加粗等修饰。

项目进程条目复用现有 wiki 记忆、出处、关系与变更记录。项目现状单独存 `project_status`（`project_id` 主键、`body` MEDIUMTEXT），只保存清洗后的正文，不参与条目生命周期，也不保存修订或来源快照；普通节点的重要结论变化仍可追溯。

模型可返回零条或多条条目建议；提交新增或更新的**项目进程条目**（`subject=project`）时，必须同时返回覆盖后的完整项目现状 Markdown；本次只提交任务或文档条目时可以省略该项目现状字段（模型返回 `null` 视同未返回，不覆盖现状）。对已有节点需引用其 ID，判断依据不足时不因标题相似合并；事件和来源去重不能代替语义判断。不同节点可引用同一来源，同一变化不因多来源或重试重复建条。

## 可靠性与恢复

- 持久化候选及处理范围，正常零产出记成功；模型失败、格式不合格、来源不可访问或写入失败保留候选并重试。
- 维护会话的持久化快照超过 10 MiB 时不整次失败：本次已校验的结果照常落库，会话换新 id、清空检查点与上下文统计，轨迹记「已重置维护会话」，下一次运行从干净上下文继续。否则历史累积会让每一次运行都在结尾失败，作业永久无法处理。
- 条目与现状覆盖在同一事务提交；失败整次重试，不产生半条，也不把失败结果写进现状。
- 通过候选信号版本与结算检查点处理重复、并发和过期结果；结算只消费已经核验的来源。
- 运行记录显示触发来源、输入范围、零产出或新增更新结果、失败原因和重试状态，提供手动重试。

## 当前实现（2026-11-04）

- 项目进程条目仍走 `agent_project_memory_queue` 候选与 `project_memory` 结算；来源核验与修订保留。
- 项目现状存 `project_status`（`project_id` 主键、`body` MEDIUMTEXT、`updated_by`、`updated_at`）；结算提交新增或更新条目时同事务整份覆盖，零新增不写。本次条目全是任务或文档且未给出正文时保留原有现状，不因正文为空整批回滚；只有项目进程条目缺正文才整次失败。写入时清洗掉标题、列表、加粗等修饰，只保存正文。
- 失败预算按内容算：同一来源产出新内容（候选来源提示变化、`signal_revision` 递增）时重置该行的失败次数与上次错误；人工「立即运行 / 重试」重置项目进程排队行的失败次数并把行拉回当前，历史失败不再让新一次重试直接落进「已停止自动重试」。
- 迁移 220 从旧现状页回填正文，删除 `project_status_nodes`、`project_status_source_snapshots`、`project_status_revisions`，旧现状页标记作废；结算状态列收敛为 `applied`。
- 读侧：`GET /api/projects/:id/memory` 的 guide 与 MCP `get_project` 的 `status` 都读这份 Markdown；面板移除现状历史与来源待核实提示。

## 验证与边界

- 已在本地独立测试库验证：新条目覆盖现状且只保留一行、零条目不覆盖、条目更新缺少现状正文时整次失败并保留候选、只提交任务条目且未给现状时条目照常写入且现状不变、项目进程条目给 `null` 时整次失败、失败次数不跨内容变化与人工重试继承、导读读取、迁移与集成路由；任务只有终态/阻塞/返工且属于主要任务才入队，普通流转与空迭代归档被过滤；`npm run lint`、`npm run build` 通过。
- 自动化使用替身模型，不能证明真实模型的判断质量；浏览器实机、完整全量回归与线上发布仍需另验。
- 19、20 号文档中关于现状修订、指纹和每日巡检的描述是历史记录，已不再适用。
