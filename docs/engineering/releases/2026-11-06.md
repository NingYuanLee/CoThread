**真因不在云侧，而在发布脚本。** 用 `OOS_RunCommand` 只读核对实例得到：

- `readlink -f /opt/cothread/current` 仍是 `/opt/cothread/releases/20261104T194437Z`（11-04 的版本）；

- `/etc/systemd/system/cothread.service` 的 `ExecStart` 仍是 `… server/index.js --production`；
- `/tmp/tmp.zhrM3MPMFn/scripts` 存在（启动钩子的 `mktemp -d` 已执行，钩子随后因脚本退出码非零而中止）。

## 3. 本轮遗留与后续事项

- **`server/` 迁移已全部完成**（199 个 `.ts`、0 个 `.js`），但迁移期间发现的缺陷分布在多处，逐条见 [server/ 的 TypeScript 迁移](../22-server-typescript-migration.md) 的「迁移后处理的两处遗留」与「迁移完成后的遗留事项」。其中影响面最大的一条是本记录第 1 节的部署路径遗漏。

- **正式库连接池上限**：本轮把默认上限从 8 提到 20（`DATABASE_POOL_SIZE` / `DATABASE_WORK_POOL_SIZE` 可覆盖）。正式库 `max_connections=10520`、`Max_used_connections=506`、当前连接 25，单实例两个池合计 36 个连接，余量充足，未调整 RDS 的 `max_connections`。

- **`docs/engineering/05-cloud-environment.md`** 已补一条 `ReleaseWaiting`（执行 `Waiting`、0 任务失败、`current` 未变）的排查路径：先用 `OOS_RunCommand` 只读看 `current` / `releases` / `logs` / 包内入口 / systemd 单元这五项，再决定是脚本问题还是云侧问题。
