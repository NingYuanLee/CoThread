## 1. 为什么返工

第二轮为了保住管理空间的字节收益，把共用规则做成「原地保留 + 另存同序副本」，实际留下 `workspace.css` 与 `shared-workspace.css` 之间 **3,185 条完全相同的规则**、`admin.css` 另有 171 条。同一批规则改一处要改两处，是实打实的维护陷阱。本轮按「维护简洁优先」改成单一来源。

<a id="r2"></a>

## 2. 改了什么

| 文件                       | 内容                                              |
| -------------------------- | ------------------------------------------------- |
| `web/workspace.css`        | 工作台专属规则（2,374 条 / 419,726 字节）         |
| `web/shared-workspace.css` | 两边共用的规则，唯一来源（806 条 / 136,056 字节） |
| `web/admin.css`            | 管理空间专属规则（60 条 / 13,689 字节）           |

跨文件重复规则 **0 条**。

拆分依据是**层叠顺序即优先级**：只有「同选择器命中同一元素 + 同属性 + 同特异性」的规则对，才会因先后变化而改变结果。做法是先建冲突关系（静态扫描 3,210 对，再用真实 DOM 补齐「不同类但同元素」的关系，共 3,256 对有效冲突），有冲突的规则绑成组不可拆，再按「只被工作台用 / 只被管理空间用 / 两边都用」分派，组内保持拆分前的先后。

一处特别处理：`.admin-account-avatar` 原本与通用的 `.avatar` 抢同一元素——静态同类扫描看不到，是 DOM 级对比抓出来的。它只被管理空间使用，因此放进 `admin.css`，由加载顺序 `shared → admin` 自然排在 `.avatar` 之后，恢复原样。

门禁 `scripts/check-css-order.mjs` 改守两条不变式：① 跨文件重复规则数必须为 0；② 覆盖关系对（记录在 `scripts/css-order-manifest.json`，含拆分前的先后）必须在同一文件内且先后不变。已接入 `npm run lint`。
