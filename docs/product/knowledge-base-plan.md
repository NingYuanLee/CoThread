# 共序知识库总计划

状态：计划。本文只定范围和顺序。不表示功能已经上线，也不改现有群聊、归档和老翁维护任务的行为。

一次部署仍是一家公司。协作主线保持不变：迭代群聊、精确文档版本、任务、归档交接、小祥执行。知识库是这条主线旁边的另一条线。

## 已定口径

- 组织是这家公司下面的部门树，不是第二家公司，也不做汇报线、编制和职级。
- 人和组织：主组织最多一个，兼岗可以有多个。现有账号允许暂时没有主组织。
- 项目和组织多对多。每条关联是「主办」或「参与」。一个项目最多一个主办。同一组织不能又主办又参与。
- 「独立项目 / 跨组织项目」不另存标记。只有一个主办、没有参与方，就是独立项目。一个主办加上至少一个参与方，就是跨组织项目。没有主办的项目不叫独立，也不叫跨组织。
- 项目 Wiki 正文只留在项目里。独立项目挂到主办组织的架上，仍是同一套页。跨组织项目给每个参与组织一条简报和链接，不复制正文。
- 页只有五种：指南、决策、复盘、术语、当前状态。每页有稳定编号、正文、状态（草稿 / 现行 / 被替代）和出处（消息、文档版本、任务、归档）。
- 公司级只有人工编写的指南和目录，不从项目或组织自动上卷全文。
- 有问必答不再是群聊模式。它是私聊，房间里只有发言人和老翁。小祥不在。按「人 + 范围」各留一份记录。范围到后面才逐级开放：先项目，再组织，再全公司。
- 私聊只读。老翁不改文档、不建任务、不往群里发言。要办事，回到迭代 @小祥。
- 老翁回答用的会话，和它整理文档、做归档的维护会话分开。
- 参与组织的成员默认只看简报，不看项目 Wiki 全文，也看不到群聊原文。
- 已经发在群里的有问必答消息留在原迭代，不搬进私聊。管理员不能默认翻看所有人的私聊。

## 不做

多公司租户、汇报线、把项目文件复制进组织、在私聊里派活、用现在那一条项目长期总结代替 Wiki 页、文件在线编辑、对象存储、多实例调度。

## 技术选型

组织、页和私聊都落在现有 MySQL 8.4.9 与现有 DSH 老翁上。不为知识库换数据库，不另起检索引擎，不升级到 MySQL 9。

2026-10-23 核对的手册：

- [MySQL 8.4 字符串类型](https://dev.mysql.com/doc/refman/8.4/en/string-types.html) 列出的是 CHAR、VARCHAR、BINARY、VARBINARY、BLOB、TEXT、ENUM、SET，没有 VECTOR。
- [MySQL 8.4 ngram 全文解析器](https://dev.mysql.com/doc/refman/8.4/en/fulltext-search-ngram.html) 是内置插件，为没有词边界的中日韩文本切块，InnoDB 和 MyISAM 都能用。
- [VECTOR 类型](https://dev.mysql.com/doc/refman/9.1/en/vector.html) 写在 MySQL 9 手册里，不在 8.4。

因此：

| 事项 | 选择 | 不选 | 原因 |
| --- | --- | --- | --- |
| 页正文 | MySQL 的 TEXT，Markdown | 文档库文件、富文本编辑器、独立 Wiki 程序 | 权限、出处和审计已经在库里。页面渲染沿用现有 Markdown |
| 检索 | 页标题和正文上的 ngram 全文索引。老翁先查页，再按出处打开原文 | 向量库；把库换成 MySQL 9 的 VECTOR | 要找的是编译后的少量页，不是把群聊切块做语义检索。多一个服务或换大版本都超出小团队单实例 |
| 问答运行时 | 现有老翁的单独只读会话加查询工具 | 另一套 RAG 服务 | 成员、模型和工具边界已经在 DSH 上 |
| 组织关系 | 普通关系表 | 图数据库 | 树和多对多用外键就够 |

全文索引只是查找工具，不是事实来源。页的正文、状态和出处仍以表为准。群聊原文不进这个索引；提问者看到的原文只来自页上已经写下的出处，并且还要过现有文档权限。用词差得远、全文索引找不到页时，先改页的标题和指引，不先加向量库。

向量工具现在也不加。嵌入模型、向量数组和独立向量库要多一套密钥、同步和备份，还要在检索前套上项目成员和主办/参与权限。页的数量在小团队里是百级，不是百万级切块。等阶段 3 的私聊真出现「全文索引找不到、但页里明明有」的提问，再考虑把向量存在 MySQL 里做页级相似度，仍然不另起数据库。

不把这条流程搬到现成框架上。2026-10-23 核对：[@langchain/langgraph 1.4.15](https://www.npmjs.com/package/@langchain/langgraph) 是长期有状态代理的编排库，负责图、检查点和人在回路，本身不是知识库。[LangGraph v1](https://docs.langchain.com/oss/javascript/releases/langgraph-v1) 也是这个定位。仓库里没有 LangChain 或 LangGraph 依赖，老翁的会话、工具和模型已经在 DSH 上。归档写页、提问查页都是短流程，不值得再维护第二套编排。

[quant-llm-wiki 0.8.1](https://pypi.org/project/quant-llm-wiki/) 是 Python 3.10+ 的量化研究工具，按 raw / wiki / schema 编译 Markdown，向量检索只作后备，并自带 LangGraph 和 ChromaDB。它不认识共序的组织、项目权限和迭代归档，不能直接接上。Dify、RAGFlow 一类整套知识库产品同样不接。

## 第一层：阶段顺序

前一阶段的完成标志没达到，不开始下一阶段的实现。

| 序 | 阶段 | 完成标志 | 达到之前不做 |
| --- | --- | --- | --- |
| 1 | 组织与人 | 能维护部门树、人的主组织与兼岗、项目的主办与参与；独立或跨组织由关联算出来 | Wiki 归属、按组织提问 |
| 2 | 项目 Wiki | 归档确认后能留下复盘页和决策页；人能打开、修改，并看到出处。现有项目长期总结仍保留 | 私聊不得假装这些页已经存在 |
| 3 | 有问必答私聊 | 群聊里不能再选有问必答。项目成员能和老翁私聊，回答点到页和出处，不能写 | 组织范围和公司范围的提问 |
| 4 | 组织架与公司目录 | 主办项目出现在组织架上；参与组织只有简报；公司页只有目录和人工指南。私聊可以选组织和全公司 | 新人默认落地 |
| 5 | 新人入口 | 没有进行中的迭代、且已有主组织时，登录落在主组织主页，可以直接问。未加入的项目看不到正文 | — |

这样排是因为：先有架子，再有页，再让人问这些页，然后才把页挂到组织和公司，最后才改登录后的落点。

## 第二层：工作包

### 阶段 1 · 组织与人

2026-10-23 已实现。管理空间「组织工作 / 组织架构」提供部门树、主组织与兼岗、项目主办与参与。独立、跨组织、未归属不落库。迁移为 `120_organizations.sql`。核对清单由 `tests/organizations.test.js` 和 `tests/admin-permissions.test.js` 覆盖。

1. 组织单元：部门树的新增、改名、移动、归档。
2. 人与组织：主组织、兼岗、从组织移出。
3. 项目与组织：设主办、加参与、撤下；界面只展示算出来的独立或跨组织。
4. 管理空间：在现有「组织工作」下增加组织架构页和权限，不改项目、迭代、任务三个老页面的职责。
5. 旧数据：已有项目和账号保持能用。不自动编造部门，也不强迫马上挂上组织。

### 阶段 2 · 项目 Wiki

2026-10-23 完成标志已核对。页在 `wiki_pages`，出处在 `wiki_page_sources`。正文是 Markdown TEXT，标题和正文有 ngram 全文索引。归档确认在同一事务里写现行复盘页和决策页，出处指向这次归档和相关任务；重复确认不另写。人在项目管理的「知识页」里打开、搜索和改正文，不改群聊。只读成员不能改。项目长期总结仍由确认后的老翁记忆任务写入。`tests/wiki-pages.test.js` 与 `tests/iteration-archive.test.js` 已通过。文档版本出处、以及文档整理时按引用改页，还没有写入路径；当前没有任何页引用文档版本，文档整理也不改 Wiki。私聊仍未开始。

1. 页模型：五种页、状态、出处。页不是文档库里的一个文件。
2. 编译：人类确认归档时，除了现有长期总结，再写复盘页和决策页。文档整理已于 2026-10-25 下线，这条「按引用改页」的写入路径当前未启用。
3. 人读人改：项目内可打开页、改正文、看见出处。改页不反向改群聊历史。
4. 和旧记忆的关系：agent_project_summaries、成员认识、文档摘要继续给 Agent 用，不删除，也不当成给人看的 Wiki。

### 阶段 3 · 有问必答私聊

2026-10-23 完成标志已核对。群聊新消息不能再选有问必答，历史消息上的 chat 仍可识别。项目里「问老翁」按人加项目各留一份记录。老翁只用现行知识页作答，并点出页和出处。这条路径不写群消息、任务或文档。`tests/wiki-questions.test.js` 已通过。组织和公司范围还没开。

1. 从群聊输入模式去掉有问必答。历史消息上的 chat 仍可识别，新消息不能再选这个模式。
2. 私聊房间：一个成员、一个项目、一份记录。换项目就是换房间。
3. 老翁只读回答：只用提问者有权看的页和出处。单独会话。不能发群消息、不能动任务和文档。
4. 入口只放在项目里。回答里带页和出处；点出处沿用现有文档权限。

### 阶段 4 · 组织架与公司目录

2026-10-23 完成标志已核对。主办组织的架上只有项目和页的标题，没有正文。参与组织只存「《标题》有更新」，撤下参与就删简报。公司目录列出组织，指南只能人工写。私聊可以选本组织或全公司；不是该组织的人不能问，公司提问也读不到项目页正文。`tests/org-shelf.test.js` 已通过。新人登录落点还没改。

1. 组织主页：本组织的指南、主办项目的 Wiki 链接、参与项目的简报。
2. 简报：项目 Wiki 更新时，给每个参与组织写短简报，不复制页。
3. 公司目录：列出组织，加上人工编写的公司指南。没有自动上卷。
4. 私聊范围：在阶段 3 的项目房间之外，开放本组织和全公司。没权限的范围不能选，也不能靠提问绕过去。

### 阶段 5 · 新人入口

2026-10-23 完成标志已核对。没有进行中的迭代、且已有主组织时，`/api/me/landing` 返回该组织；打开站点根路径会去管理空间的「我的组织」，那里可以直接问。带 `stay=workspace` 仍进工作台。没有主组织的人仍进工作台。未加入的项目不能打开知识页正文，也不能对那个项目提问。回答不会自动发到群里。`tests/newcomer-landing.test.js` 已通过。

1. 落地：没有进行中的迭代、且已有主组织时，打开主组织主页，而不是空的群聊。
2. 没有主组织的人仍进现在的工作台。
3. 未加入的项目不能问、不能看正文。把回答带进群里由本人自己复制，系统不代发。

## 第三层：阶段 1 可开工拆分

这一层已经按下面的拆分落地。阶段 2 及以后的第三层，等上一阶段的完成标志达到后再拆，避免现在把页、私聊和入口的细节写死。

### 数据

- 组织：编号、上级、名称、排序、归档时间。上级不能形成环。公司本身没有单独一行，这一次部署就是公司。
- 人与组织：组织、人、关系（主组织或兼岗）。一个人最多一条主组织。停用账号不自动丢掉关系，但主组织选择里不出现已停用账号。
- 项目与组织：项目、组织、角色（主办或参与）。同一项目最多一行主办。同一对「项目 + 组织」只有一行。
- 派生：有主办且参与数为 0，视为独立。有主办且参与数大于 0，视为跨组织。没有主办，视为未归属。不写回数据库。
- 变更记入现有项目或账号审计能覆盖的就沿用；组织树本身的新增、改名、移动、归档要有记录。不记录密钥或正文。

### 规则

- 仍有下级、仍有主组织成员、或仍是某项目主办的组织，不能硬删，只能归档。归档后不能再被选为新的主办或主组织。
- 更换主办、增加或撤下参与，是明确操作，不能靠改一个下拉框顺手完成。
- 未归属的项目在工作台里和现在一样可用。文档、迭代、任务、归档都不检查组织。
- 现有成员不填主组织也能登录。主组织成为默认落点是阶段 5 的事。

### 管理空间

- 「组织工作」增加「组织架构」页。权限拆成：查看、维护组织树、安排人员、设置项目归属。只给页面时只读。
- 页上是一棵树。选中组织后看人员与项目。项目一行显示独立、跨组织或未归属，标记不可编辑。
- 「我的工作」本阶段不加组织页。项目、迭代、任务的原权限键不改含义。

### 本阶段完成时要能核对

- 建出至少两级部门，把一个人设成主组织、另一个组织设成兼岗。
- 一个项目只设主办时显示独立；加上参与组织后变成跨组织；撤掉全部参与后回到独立。
- 试图给第二个主办、或让主办组织同时成为参与方时，保存失败。
- 没有任何组织关联的旧项目，工作台仍能打开、发言和归档。
- 没有组织架构权限的成员不能改树、不能改归属。

### 本阶段明确不包含

Wiki 页、私聊、从群聊移除有问必答、组织主页、公司指南、登录落点。群聊模式列表保持现在的四项，直到阶段 3。
